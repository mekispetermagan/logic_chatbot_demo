# Demo conversation API

A small FastAPI application using Python's built-in SQLite library. Requires
Python 3.10 or newer. First build the editor from `backend/logic_engine/`:

```sh
cabal build exe:logic-engine-editor
mkdir -p bin
cp "$(cabal list-bin exe:logic-engine-editor)" bin/logic-engine-editor
```

Then run from `backend/api/`:

```sh
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
uvicorn app.main:app --reload
```

The real entry point is `app/main.py`; there is no root forwarding script or
packaging configuration. Interactive API documentation is at `/docs`.

## Endpoints

- `POST /conversations` with `{"domain":"objects"}` or `{"domain":"network"}`: creates a random UUID conversation and its
  initial toy-world snapshot. Returns HTTP 201 and a `Location` header.
- `GET /conversations/{id}`: retrieves the latest stored world. Unknown UUIDs
  return 404; malformed IDs return 422.

The backend also supports `{"domain":"cellular"}` for a 16×16 toroidal cellular
automaton. New conversations contain a centered black/white Game of Life glider.
`POST /conversations/{id}/step` with no body advances one synchronous generation,
returning the full state, `changedCells`, and feedback. Its world stores `cells`,
`ruleset`, `generation`, and `rulesetRevision` rather than an object list. Models
support 2–6 active colors and arbitrary valid neighbor-count rule sets. Stepping,
Undo, save/load and the Flutter player are integrated. Cellular chat supports
all three layers of [Cellular v2](../../docs/cellular-language-v2.md),
including ruleset editing, same-color connectivity, forecasts and bounded
stabilization questions. The shared LLM preview/accept/reject flow is available.
`POST /conversations/{id}/cell` with `{"position":{"x":0,"y":0},"color":"black"}`
paints one cell using an active palette color. Haskell validates and updates it;
generation and rules stay unchanged. Changed cells add one Undo step; unchanged
colors add none. Out-of-board coordinates and inactive colors return HTTP 422.
`POST /conversations/{id}/ruleset` takes the complete `ruleset` plus optional
`refill: true` to authorize a random refill when board colors are removed.
Haskell validates and applies the change atomically. Rules-only edits preserve
generation; refills restart generation zero. The rules revision increases once
per change, and Undo restores the whole pre-submission state. Equivalent or
unchanged rulesets add no history. Random seeds are generated by the server;
the public endpoint accepts no seed or client-supplied board.
Startup expands old 8×8 cellular snapshots and slots with centered white padding,
preserving rules, generation and history. Object/network boards remain 8×8. See the
[cellular backend contract](../../docs/cellular-automata-backend.md).

All three domains return `conversationId`, `domain`, `world`, `canUndo`, ordered `messages`, and nullable `pending`. Object/network world JSON has `width`,
`height`, and `objects`; each object has an integer `id`, a required `attributes`
map of canonical attribute/value strings, and nullable `position`. A present
position requires integer `x` and `y`, zero-based with A1 at the bottom left.
Absent attributes are omitted. Domain initial worlds live in
`backend/shared/toy_world.json` and `backend/shared/network_world.json`.

## Editing

All editing endpoints use `POST /conversations/{id}/...` and return
`conversationId`, `domain`, `world`, `canUndo`, messages, pending, and concise `feedback`:

| Endpoint suffix | JSON body | Action |
| --- | --- | --- |
| `property` | `{"position":{"x":0,"y":0},"property":{"attribute":"color","value":"red"}}` | Apply one property; create on an empty square |
| `ports` | `{"position":{"x":0,"y":0},"ports":["north","east"]}` | Replace network ports atomically, preserving color |
| `place` | `{"objectId":5,"position":{"x":0,"y":0}}` | Place an existing unplaced object |
| `erase` | `{"position":{"x":0,"y":0}}` | Remove the object on a square |
| `clear` | No body | Empty the world, including unplaced objects |
| `undo` | No body | Restore the previous snapshot |
| `slots/{slot}/save` | `{"overwrite":false}` | Save the committed world and salience ranking in slot 1–5 |
| `slots/{slot}/load` | No body | Restore a saved setup as one undoable step |

Every conversation response includes five `worldSlots` entries, each containing
`slot` and nullable `savedAt`. Slots belong to one conversation (and therefore
one domain), survive restarts, and remain saved after Undo or Clear. Empty worlds
can also be saved. Saving does not advance world history or change reference
context; overwriting requires `{"overwrite":true}` (otherwise HTTP 409).
Loading preserves object identifiers, restores the saved salience ranking, keeps
the conversation's identifier allocator moving forward, and appends a short chat
message plus an event for the interpreter agent. Chat history and the LLM session
are retained. Undo restores the complete state from before loading. Empty slots
return 404; invalid slot numbers return 422. Save/load is blocked with HTTP 409
while an interpretation or symbolic clarification is pending. The slot table is
added automatically on startup to existing v2 databases without removing data.

Properties are explicit attribute/value pairs validated by Haskell. Objects use
color, size, and shape; networks use color and unary north/east/south/west ports.
JSON and served v2 grammars use canonical names; natural synonyms belong to LLM interpretation in all three domains. Invalid pairs return 422
without saving history. Coordinates are zero-based; Objects and Network use
8×8 boards, while Cellular uses a separate 16×16 cell model.
Placement preserves identity and attributes and requires an empty destination.

FastAPI sends the stored world and structured action to the Haskell executable.
Haskell owns world edits and semantic checks. `LOGIC_CHATBOT_ENGINE_PATH`
overrides the default `backend/logic_engine/bin/logic-engine-editor` path.
Calls time out after five seconds. Missing/broken engines return 503 without
changing history. Creation/retrieval and Undo work without the executable.

Malformed requests return 422; unknown conversations return 404. Blocked actions
(occupied destinations, coordinates outside the board) return 200 with the
unchanged world and feedback. Changes to world or discourse state create snapshots. Each edit
is a SQLite transaction covering retrieval, evaluation, and persistence. Undo
retains the initial snapshot; editing after Undo starts a new history branch.

## Chat

### Full conversation reset

Send `full reset` through the existing chat endpoint. It is case-insensitive,
ignores surrounding/repeated whitespace and accepts an optional final period.
FastAPI asks for confirmation without invoking Haskell or the LLM. Replies carry
`resetPending:true`; `yes` confirms, `no` cancels (also case-insensitive, optional
period). Other replies repeat the question. Confirmation survives restart.
While waiting, edits, Undo, save/load, interpretation review and symbolic choices
return HTTP 409. Reset is available even during an existing review/clarification;
cancelling preserves it.

Confirmation atomically creates a new conversation in the same domain and
deletes the old world's history, chat, proposals and agent-session link. Objects
and Network start empty; Cellular restores its initial Life glider at generation
zero. There is no Undo. All five saved slots and their salience rankings transfer unchanged.
The allocation counter is retained so restored slot identities remain valid.
The new conversation gets a fresh interpreter session on its next LLM call.
Global spending records and file transcripts remain intact; no model call is
needed to reset.

The reply has a new `conversationId` and `resetFrom` containing the old ID. Clients
must persist the new ID and clear their old composer/history state. A small ID
handover receipt allows GET or chat retries against the old ID to return the
replacement with `resetFrom`, without executing that stale request. Other writes
to the old ID return 404. Repeated resets update receipts to the latest ID.

### Controlled entries

`POST /conversations/{id}/chat` accepts a `text` entry. Object conversations use
[Objects v2](../../docs/object-language-v2.md), for example:

```json
{"text":"Set color of #0 to blue. Does #0 satisfy (color is blue)?"}
```

Commands require final periods; questions require question marks. A square is
always a location; use `the object at A4` for its occupant. Creation is explicit,
and a failed creation or move never leaves a new fallback object. A normal
sequence stops on failure and retains completed steps. Every conceptual command
is atomic. `atomically { Set color of #0 to blue. Move #0 to A4. }.` commits
both domain and salience changes or neither.

Object commands include nullable-position exchanges, attribute copy/transfer/
exchange, cloning, frozen bulk selections, explicit rearrangements and verified
rotation/reflection macros. Position and appearance transformations preserve
or change different state and are presented distinctly in review. The grammar
shares typed Boolean predicates across checks, selections, counts and quantifiers.
Network uses the same explicit execution policy, with graph and port macros.

Feedback includes canonical sentences, resolved identifiers and answers or
identity-specific changes. `changes` contains `objectId`, `kind` and `detail`;
kinds distinguish creation, deletion, movement and appearance updates. Parse
errors preserve domain/discourse state. Blank or malformed request bodies return
422. Engine failures persist neither messages nor snapshots.

The complete `Undo.` entry requests the same operation as the Undo
button, restoring world and salience while retaining chat and allocation history.
It accepts case-insensitive spelling and surrounding whitespace, but no suffix
or additional sentence in either domain.

Objects and Network record object and square antecedents separately, on one recency
clock. Pronouns use the operand's required type; shared predicates can ask which
kind is intended. A square mention never implies a mention of its occupant.
Mixed ties populate both object candidates and square choices. Existing `/clarify`
bodies select one type explicitly. Typed rankings remain opaque JSON to Python;
world/salience snapshots, preview, restart and Undo preserve both kinds.

Ambiguity returns `pending` with the affected `sentence`, candidates,
`squareChoices`, or `groupingChoices`. Resume through
`POST /conversations/{id}/clarify`, supplying exactly one of `{"objectId":3}`,
`{"position":{"x":3,"y":4}}`, or `{"groupingId":1}`. Haskell checks
the offered choices. Invalid choices leave state unchanged. Further ambiguity
can pause again; all rounds remain one Undo unit and survive restart.

Objects v2 and Network v2 accept readable syntax without redundant parentheses around
descriptions, appearance values, offsets or simple conditions. Boolean operators
have no implicit precedence in surface input. Missing grouping that permits
different scopes produces explicitly parenthesized choices before the entry
executes. This clarification is deterministic and does not invoke the LLM.

Pending state in Objects and Network also carries an opaque versioned `payload`: the frozen entry
seed and accepted choices used for deterministic continuation. A paused atomic
batch returns its private world as `pending.stagedWorld`; `world` remains committed
state. The frontend labels provisional display explicitly. Completion commits
once; failure or Undo discards staged changes. Clients do not construct payloads.
Legacy continuations are rejected; all three domains use v2 only. Ordinary edits/new chat remain blocked while clarification is pending.

Conversation replies include `languageVersion` (`objects-v2`, `network-v2` or
`cellular-v2`) and `nextObjectId`. Object/network identity allocation is persisted
outside Undo snapshots and advances even when reserved staged IDs are abandoned.
Clear and deletion never reset it; allocation starts above each initial world's
greatest identifier. Cellular has fixed cells and keeps the counter at zero.
See the [JSON contract](../../docs/json-contract.md) for versioning,
interpretation version checks, and the exact persistence fields.

## Optional LLM translation

The default transport is now **persistent OpenAI Agents sessions**. FastAPI
creates a saved Objects, Network or Cellular agent lazily on first use, then stores one
session ID per conversation in SQLite. The approved instruction source is
[`agent-instructions-draft.md`](../../docs/agent-instructions-draft.md).
Editing it updates the same saved agent on next use and starts a fresh LLM
session while preserving the application's world/chat/Undo history. The key
must permit Agents read/write operations and model inference. Luna is preserved;
unsupported model or permission errors are reported without silently switching.

No tools, subagents or hosted environments are enabled. Acceptance/rejection,
visual edits and Undo are queued for the next requested agent turn, along with
the current world. No decision or preview triggers an extra GPT call. See
[Persistent Interpreter Agents](../../docs/agent-sessions.md) for lifecycle
and accounting details. `LOGIC_CHATBOT_LLM_BACKEND=responses` explicitly restores
the earlier transport; it is not an automatic fallback.

Agent JSON now includes a separate `reply` field and reply-only `conversation`
status. Clear greetings, thanks and conventional courtesy receive a short
ordinary chat reply; unrelated substantive discussion receives a brief neutral
scope decline. Conversational text never becomes a candidate program. Mixed
greetings and tasks still require review of the task translation. Reply-only
exchanges preserve world/salience/Undo state and any pending interpretation
clarification. They use the existing chat/answer endpoints and normal LLM
accounting, with no additional frontend fields. The LLM switch must be on for
ordinary conversational chat; disabled mode remains strict controlled English.

The Flutter app-bar switch opts individual chat requests into syntax correction:
`{"text":"paint A1 red","useLlm":true}`. It defaults to false. Haskell checks
syntax first; valid controlled English and semantic failures never invoke Luna.
GPT offers up to three ranked readings with explanations and a targeted question
when ambiguous. Haskell syntax-checks every candidate; no candidate is executed
automatically. The original prompt and proposal are persisted for review.
Flutter offers **Preview**, **Accept**, and **Reject**. Preview shows a temporary
board and feedback without changing world/salience history. Accept applies the
selected stored entry as one undoable step. Reject restores the original prompt
for editing. Even a single reading or translated question requires acceptance.
Missing information can produce a clarification question without candidates.
Reply in the existing input and choose **Submit answer**: GPT receives the
original request, its question and all previous answers, and offers a fresh
proposal. Rejected programs remain visible with Haskell's parser reason,
separate from clarification questions. Failed validation also allows a
correction via Submit answer. Object/square clarification still works after acceptance.
The prompt allows general knowledge, coordinate calculations and planning a
sequence of supported commands. Haskell validates and evaluates the complete
entry. The current world is included for selecting targets and planning around
existing objects. Agents retains its conversation; Haskell salience and web
lookup tools are not supplied.
The complete world is included in each interpretation input. Responses counts
input tokens before generation; Agents bounds new input to 40,000 UTF-8 bytes
and accounts for reported turn usage. If the conversation changes during
translation or review, preview/accept are refused with HTTP 409;
reject the stale proposal and resend manually.
An unsupported interpretation now includes the model's brief reason, labelled
`LLM explanation: ...`, in the saved feedback. This text is bounded and redacted.

With normal Uvicorn INFO logging, look for `GPT reply` in the backend terminal:
it shows status, ranked translations, question, explanation, response ID, token counts and cost.
`GPT parser rejection` adds Haskell's feedback when a proposed translation fails
syntax checking. Invalid model JSON and incomplete replies are logged separately.
Logs are bounded, escape control characters and redact keys. The prompt, world,
HTTP headers and hidden reasoning are excluded. No extra logging switch is needed.

Full API exchanges are also appended to `logs/gpt-conversation.jsonl`, created
automatically at startup and ignored by Git. Each JSON line has a UTC timestamp
and event; request/response pairs include conversation and attempt IDs. It
records complete prompts, examples, world snapshots, entries, response bodies,
usage, provider errors, transport errors and parser-rejection feedback without
the console's length limit. Credential headers/fields, the configured key and
OpenAI-style keys in text are redacted. Returned metadata is retained exactly
apart from redaction; hidden reasoning unavailable from the API cannot be logged.
Logging starts with future calls and appends across reloads/restarts.
`LOGIC_CHATBOT_LLM_LOG_PATH` overrides the default file location. From `backend/api/`:

```sh
tail -f logs/gpt-conversation.jsonl
```

Create a **secret API key** at https://platform.openai.com/api-keys, then paste
that generated key at the terminal prompt below; do not choose a password.
Configure it in the same terminal that runs the backend. From
`backend/api/`, after activating the virtual environment:

```sh
read -rs -p 'Paste your OpenAI API key: ' OPENAI_API_KEY
echo
export OPENAI_API_KEY
uvicorn app.main:app --reload
```

The hidden prompt keeps the key itself out of shell history. Do not paste the
key into chat or Flutter configuration. `.env` files are ignored by Git; this
app reads environment variables and does not automatically load `.env` files.
No additional Python dependency is needed. Without a key, the rest of the demo
works and a requested correction reports that LLM is not configured.

Translation failures report the stage (token counting, generation, usage or
translation validation), HTTP status and recognized provider error code/parameter.
The backend also logs the provider's `x-request-id` when available. For example,
`generation request: HTTP 429; code=insufficient_quota` identifies a quota issue.
Keys, raw responses, provider messages and exception text are never included in
these diagnostics. Unknown provider codes are omitted. Retry the entry manually
after addressing the reported issue; there are no automatic retries.

The experiment admission budget is **$1 total**, shared across all domains and
conversations and preserved across restarts. `llm_requests` stores maximum
reservations and estimated token costs independently of world snapshots. The
optional Responses transport caps input at 20,000 tokens and output at 2,000
including reasoning; Agents manages context and output length and limits this
app's new input to 40,000 bytes. Agent usage is best-effort, without separate
cache-write counts; estimates charge noncached input at the higher write rate.
The local guard cannot guarantee a hard cap on an in-flight managed turn. Every
generation reserves $0.0035 first; uncertain attempts keep that reservation.
There are no automatic retries and Undo/Clear cannot refund or reset spending.
Do not delete or change the database to restart experiments unintentionally.

Responses include `llmBudget` with `limitUsd`, `spentUsd`, `reservedUsd`,
`remainingUsd`, and `requestCount`. A machine message from an LLM attempt also
has `llm` metadata: status, model, translation, token counts, calculated
`costUsd`, and any `reservedUsd`. Token cost is a local estimate at the pinned
rates; compare it with the provider's usage dashboard. Mocked HTTP tests incur
no API charges. See [LLM translation](../../docs/llm-translation.md)
for the prompt files, budget assumptions, and limitations.

Review endpoints return normal edit state:

| Endpoint under `/conversations/{id}` | Body | Behavior |
| --- | --- | --- |
| `/interpretations/{proposalId}/preview` | `{"rank":1}` | Return temporary world/feedback in `preview`; keep actual state unchanged. |
| `/interpretations/{proposalId}/accept` | `{"rank":1}` | Evaluate the stored candidate and consume the proposal. |
| `/interpretations/{proposalId}/reject` | None | Discard the proposal; keep world/history unchanged. |
| `/interpretations/{proposalId}/answer` | `{"text":"Use isolated nodes."}` | Interpret the answer in context and replace the draft; do not apply it. |

All four use POST. Preview, Accept and Reject make no GPT calls; Submit answer
makes one new bounded call under the existing $1 budget. Pending proposals and
accumulated answers survive restart and
appear as `proposal` in GET responses; previews do not persist. Editing, chat,
clarification and Undo are blocked while review is pending. Consumed proposals,
invalid candidate choices and stale preview/accept requests return HTTP 409.
Accepted/rejected drafts remain in `interpretation_proposals` for auditing,
separate from `world_snapshots`; neither rejection nor Undo refunds paid usage.
Submitting an answer retires the previous draft as `rejected` and saves its
replacement atomically. Provider failures leave a reviewable failure draft,
without keeping an earlier interpretation executable. No answer or proposal
changes world/salience history until acceptance.

## Persistence

Flutter web development uses port 8080. CORS allows `http://localhost:8080` and
`http://127.0.0.1:8080` by default. Set `LOGIC_CHATBOT_CORS_ORIGINS` to a
comma-separated list of exact browser origins for other ports or deployment.
Android and Linux native clients do not require CORS configuration.

`LOGIC_CHATBOT_DB_PATH` sets the SQLite file location. The default is
`backend/api/data/conversations.sqlite3`, independent of the working directory.
Parent directories and tables are created during application startup. Each
conversation and its initial snapshot are inserted in one transaction.
`conversations` stores IDs, immutable domains, semantic versions, non-undoable allocation counters, and creation times; `world_snapshots` stores ordered
JSON worlds, salience rankings, and nullable pending entries, starting at sequence 0. The latest snapshot is the current state.
`canUndo` becomes true when that sequence is greater than 0. Keep the database
file and its SQLite sidecars on persistent storage when deploying.

There is no authentication, cookie, shared conversation, or session expiry.
Clients will retain their conversation ID to resume after restart. The API
offers controlled-English chat. Semantic world validation and updates belong to Haskell;
Python schemas validate only the transport shape. Flutter calls these endpoints
for visual edits and uses the returned world, feedback, and `canUndo` state.

## Tests

```sh
python -m unittest discover -s tests -v
```

Tests use temporary databases and cover isolation, restart persistence,
initialization, rollback, database constraints, missing IDs, and partial objects.
Editing tests call the real Haskell executable, so build/copy it first using the
commands above. They cover all editing endpoints, history, blocked actions, and
engine failures. `LOGIC_CHATBOT_ENGINE_PATH` can select a test binary.

## Domain contract

Creation requires a domain identifier: `objects`, `network` or `cellular`.
Missing or unsupported identifiers return HTTP 422 without creating a conversation.
Every conversation response includes `domain`. Editing, chat, clarification, and
undo inherit it from the conversation; clients cannot change it through those endpoints.
FastAPI forwards it in each Haskell request and checks the response identifier.
All three domains use their explicit v2 grammars. New SQLite databases use
`user_version = 2`; existing v2 databases are retained, with additive schema
updates and centered expansion of older cellular boards to 16×16. Other schema
versions are rejected unchanged. The original object/network v2 release required
a fresh database and discontinued legacy continuations; startup does not erase
current data. The client recreates a conversation when its saved ID returns 404.
Undo restores world and salience together within the same domain.

Flutter uses generic attribute pairs and atomic port-pattern edits. The network
language includes graph construction, color-scoped questions and distinct port,
position, appearance and drawing operations. See [Network v2](../../docs/network-language-v2.md)
and the [JSON contract](../../docs/json-contract.md).
